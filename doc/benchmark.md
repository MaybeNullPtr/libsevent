# libsevent 性能测试报告

> 基于 select() 多路复用的 TCP echo server 压测结果。
> 测试环境: Linux 6.8.12, x86_64, GCC 11.4.0, Python 3.x (client)

## 测试结论

| 指标 | 数值 | 说明 |
|------|------|------|
| 最大吞吐量 | **81 MB/s** | 64KB 大消息, 50 并发连接 |
| 最大 QPS | **~67,000** | 64B 小消息, 200 并发连接 |
| 最大连接数 | **900+** | 接近 FD_SETSIZE(1024) 极限, 零错误 |
| IOPS | **2,400–4,800 ops/s** | 受 select() 扫描 + read/write 系统调用限制 |
| 内存泄漏 | **0** | 34 单元测试 + 内存跟踪验证, alloc == free |

## 详细压测数据

### 吞吐量 vs 消息大小

消息越大, 每次 I/O 搬的数据越多, select 固定开销被摊薄, 吞吐越高。

```
81 MB/s ┤         ● ← 64KB
        │
        │
        │
37 MB/s ┤      ● ← 8KB
        │
        │
        │
 9 MB/s ┤   ● ← 4KB
        │
        │
 4 MB/s ┤──●──●──● ← 64B (200/500/900 连接)
        │
        └───────────────────────
          固定开销  数据拷贝    网卡
           (select)  (read/write) 瓶颈
```

| 消息大小 | 连接数 | 总数据 | 耗时 | 吞吐量 | 往返次数 | IOPS |
|---------|--------|-------|------|--------|---------|------|
| 64B | 50 | 1.5 MB | 0.38s | 4.0 MB/s | 25,000 | 65,789 |
| 64B | 200 | 2.5 MB | 0.59s | 4.1 MB/s | 40,000 | 67,797 |
| 64B | 500 | 3.1 MB | 0.79s | 3.9 MB/s | 50,000 | 63,291 |
| 64B | 900 | 2.8 MB | 0.78s | 3.5 MB/s | 45,000 | 57,692 |
| 4KB | 100 | 390 MB | 41.2s | 9.5 MB/s | 100,000 | 2,429 |
| 8KB | 200 | 312 MB | 8.29s | 37.7 MB/s | 40,000 | 4,826 |
| 64KB | 50 | 625 MB | 7.71s | **81.1 MB/s** | 10,000 | 1,297 |

### 连接数扩展性

```
  QPS
 70k ┤      ●
 65k ┤●     ●     ●
 60k ┤           ●     ●
 55k ┤
     └───────────────────
       50   200   500   900
              连接数
```

**64B 小消息下 QPS 稳定在 57k–67k**, 从 50 连接扩展到 900 连接无明显衰减。

### 真正的瓶颈

```
                   ┌──────────────────────┐
                   │  read()  syscall      │  ← 真正的瓶颈:
                   │  write() syscall      │     内核态 ↔ 用户态数据拷贝
                   └──────┬───────────────┘
                          ↓
                   ┌──────────────────────┐
                   │  用户回调处理         │  ← 几乎可忽略
                   └──────────────────────┘
```

- **小消息瓶颈**: `read()`/`write()` 系统调用固定开销 (每次 ~0.5–2µs)
- **大消息瓶颈**: 内存带宽, 单核 ~80 MB/s (DDR4 约 20–30 GB/s, 但受 syscall 和 socket buffer 限制)
- **连接数瓶颈**: FD_SETSIZE = 1024 硬限制 (select 本身); poll 无此限制但性能一致

### 与主流框架对比 (参考)

| 框架 | 模型 | 极限吞吐 | 最大连接 | 代码量 |
|------|------|---------|---------|-------|
| libsevent | select | ~80 MB/s | ~1000 | ~400 LOC |
| libevent | epoll/kqueue | ~2 GB/s+ | 10万+ | ~50k LOC |
| libuv | epoll/kqueue/IOCP | ~2 GB/s+ | 10万+ | ~100k LOC |

libsevent 定位是 **简单、低内存、够用**——不是来跟 epoll 框架比性能的。

## 内存

通过 `sevent_set_allocator` 跟踪验证:

- 单个 `sevent_context`: ~120 bytes (含 self-pipe fds)
- 每个 `io_handle`: ~40 bytes (链表节点)
- 每个 `timer_handle`: ~40 bytes (链表节点)
- 每个 post 任务: ~24 bytes (链表节点)
- 全部释放: alloc_count == free_count 验证通过

## 测试方法

```bash
# 单测
cd build && make check

# 性能测试
python3 benchmarks/bench_echo.py --clients 200 --size 4096 --count 1000
python3 benchmarks/bench_echo_mp.py --clients 100 --size 8192 --count 200
```

- 客户端: Python socket, 多线程/多进程并发
- 测量: 发送字节数 / 总耗时
- 校验: 发送量 == 接收量, 零错误
